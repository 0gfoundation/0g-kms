# 0g-kms

Distributed key-management service for 0G tapps: a cluster of TEE (TDX) nodes that derives
per-app secrets via a **threshold-BLS DPRF**. The master key is generated by a distributed DKG
(no dealer), split across nodes, and **never reconstructed anywhere** — any `threshold` of `n`
nodes derive; fewer learn nothing.

```
app_key = KDF(σ),   σ = Σ λ_i · f(i)·H(bind(app_id, material)) = master·H(...)
```

Each node signs the derivation message with its own share locally; the coordinator combines
`≥ threshold` partials by in-group Lagrange. Derivation is deterministic, one-way
(σ → master is a discrete log, so one leaked app key exposes nothing else), and bound to both
`app_id` and caller-supplied `material`.

## Properties

- **No single point.** Genesis is a leaderless DKG (gennaro); derivation never reconstructs the
  master; a lost share is repaired by resharing — the master survives any `< threshold` loss.
- **Self-healing.** A restarted/replaced node rejoins from any `≥ threshold` **live**
  share-holders (not full membership). Shares carry a monotonic **epoch**; a node stranded on a
  stale polynomial detects it via gossip and re-syncs automatically. Dead peers are excluded by
  direct-evidence liveness and can neither stall sessions nor slow derives.
- **Proactive security.** `/refresh` rotates every share onto a new polynomial (same master):
  previously-leaked shares expire, derived keys never change.
- **Restart persistence.** Shares can be sealed (ECIES to the node's own TEE key) and reloaded
  across app restarts — the only mechanism that works at the threshold floor. A new TEE identity
  cannot decrypt an old blob (crash ≠ restart), and a stale blob is rejected by epoch.
- **On-chain anchored identity.** Membership and authorization come from the TappRegistry
  nodeList (`getNodeList(app_id)`); every request is an EIP-191 signature recovered and checked
  against it (cached, 30s TTL). No shared secrets between nodes.

## Quick start

### Local 3-node cluster (no chain, no TEE)

```bash
cd test/local-cluster
docker compose -f docker-compose.test.yml up --build -d
# wait for "genesis DKG complete" on all three, then derive:
cd ../..
cargo run --example dprf_client -- http://localhost:9101 0g-kms aabbccdd \
  0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80
```

See `test/local-cluster/README.md` for the full scenario list (threshold, recovery, refresh).

### Production (real TEE + on-chain registry)

One node per host, deployed as a tapp. Build & push the image (`Dockerfile`; needs `protoc` if
building natively), give each host its own `kms.toml`, register the nodes in TappRegistry, and
start via tapp-cli — the nodes discover each other, wait for the full nodeList, and run genesis
together. Full runbook: `docs/TESTNET_E2E.md`; lifecycle reference: `docs/CLUSTER.md`.

## Configuration (`kms.toml`)

```toml
[server]
bind      = "0.0.0.0:9090"   # HTTP: /app-key /refresh /peers /sealed-share
grpc_bind = "0.0.0.0:9092"   # inter-node gRPC

[tapp]
app_id     = "my-kms"        # KMS's own app_id in TappRegistry
tapp_ip    = "host.docker.internal"
tapp_port  = 50051
# tapp_socket = "/run/tapp/tapp.sock"   # optional Unix-socket to the local tapp-server
# mock_tee = true              # dev/CI only: key from MOCK_APP_PRIVATE_KEY env

[chain]
rpc_url          = "https://evmrpc-testnet.0g.ai"
contract_address = "0x…"       # TappRegistry

[cluster]
threshold   = 2
total_nodes = 4
self_url    = "http://<this-node-ip>:9092"   # how peers reach THIS node
seeds       = ["http://<peer-ip>:9092", …]   # bootstrap contacts (list several)
# sealed_share      = "<base64url>"      # reload this share at boot (omit = fresh start)
# sealed_share_path = "/data/share.seal" # auto-persist target (needs a durable volume)
```

`KMS_SEALED_SHARE` / `KMS_SEALED_SHARE_PATH` env vars override the two sealed-share fields.

## HTTP API

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /app-key` | EIP-191 by a signer of the **requested** `app_id` | derive; response ECIES-encrypted to the caller |
| `POST /refresh` | EIP-191 by the **app owner** (`Refresh:{ts}`) | proactive share rotation (needs all members healthy, single epoch) |
| `GET /peers` | — | liveness/epoch view, `cluster_epoch`, `live_share_holders` |
| `GET /sealed-share` | — | latest sealed blob (ciphertext; for restart re-injection) |

## Operational invariants

- **Keep `≥ threshold + 1` live share-holders** — at exactly `threshold` the cluster still
  derives but can no longer heal a loss, and a holder restart without a sealed share is fatal.
- **Restart shardless nodes one at a time** (wait for `reshare recovery complete`) — concurrent
  rejoins are the one accepted-risk gap (#6).
- **Refresh only when everyone is healthy** — it is proactive and can wait.
- **On a re-genesis** (new master — deliberate, destructive): omit/clear all sealed-share blobs.

## Status / known limitations

- Genesis requires all `n` present (first cut).
- Committee resize (change `n`/`threshold` without re-genesis) — planned, #3.
- Concurrent shardless rejoins can fork one epoch — operationally controlled, #6.
- Peer discovery bootstraps from config `seeds` (list several to avoid a bootstrap SPOF);
  fully on-chain discovery needs a registry field for the KMS endpoint.
